# Code, tests and releases

## Code

Go, at the latest stable release, pinned by `go.mod`'s `toolchain` line. One module, `github.com/lanescape/actions`, with each action's `action.yml` and program in `<name>/`. It depends on `github.com/lanescape/runners` at a version `go.mod` names, for the forwarder and for the service and emulators the tests run against. The service's interface for actions, its spec 0005, is what the actions may rely on; nothing else of the service's. Until lanescape/runners' implementation merges to its main and is tagged, `go.mod` pins a commit of its `implementation` branch, `3b97feb`, as a pseudo-version; moving that pin to a release is a pull request of its own, as below.

The code the actions share is in `internal/`: the job's runtime (inputs, outputs, summary, masking), the run's event, where an action is, a reader of files through GitHub's API, the job's OIDC tokens, the client for the service's interface, the format of `.github/runners.json`, and selectors and keys. An action yet to come adds its calls to the service's client and its program in `<name>/`, and reuses the rest.

## Tests

Every behaviour in specs/0001-actions.md has a test. They run against the real runner service, built from the version `go.mod` names, with that repository's own emulators of GitHub, Compute Engine and Cloud Storage, never anyone else's. End-to-end tests run each action as GitHub would, inside the organization and outside it: a pull request's run through to its saves, a fork's run falling back to GitHub's runners, a fork's pull request into an organization repository, an approved contribution, and the service answering that GitHub couldn't be reached. The actions' tests run natively on Blacksmith's Linux amd64, Linux arm64 and macOS arm64 machines, since paths, shells, signals and file locking differ between them, and CI builds every program for every platform it targets.

The service's command reaches only GitHub and Google themselves, and the packages it's made of are internal to its module, so `servicetest/` builds it for the tests. It's a module of its own, never part of an action, whose path, `github.com/lanescape/runners/actionstest`, lies inside lanescape/runners' so that Go lets it import those packages, as that repository's own end-to-end tests do. It requires lanescape/runners at the version `go.mod` names, which a test checks, runs the service's handler with its own Cloud Storage emulator for the bucket, checks jobs' tokens against the GitHub emulator's OIDC issuer and runs against the GitHub emulator's API, and serves the interface for actions. It stands in until lanescape/runners offers a way of its own to run its service against its emulators, and must follow that repository's internal packages when the pin moves.

The end-to-end tests, in `e2e/`, build each program as the actions do, with one difference: the build tag `e2e`, which no `action.yml` uses, makes a program call the test service, named in `LANESCAPE_TEST_SERVICE`, in place of `endpoints.Service`, and wait milliseconds between retries. They run each program with a job's environment, event payload, output and summary files and OIDC token endpoint, as GitHub would, and check that no token handed to a job appears in its log unmasked. Unit tests run each program's logic in-process against the GitHub emulator. Other tests run the actions' own steps that find Go and build a program under a job's hostile Go settings, and `release.yml`'s step that moves the tag against a stand-in for `gh`, for each case it creates, moves, leaves or refuses to move the tag. Every test uses lanescape/runners' own emulators; `go test -short` skips the end-to-end ones. The tests of `save`, and the run through to its saves, come with `save`.

Moving to a newer `lanescape/runners` is an ordinary pull request that changes `go.mod` and `servicetest/go.mod`, so its tests show the actions still work with that service before anything relies on it.

## CI and releases

Workflows here run on Blacksmith, never on the runner service's own machines, so a broken service can never stop its actions being fixed. A pull request from a fork runs on GitHub's runners instead; it needs no credentials, since nothing in CI does.

- **`ci.yml`, on pull requests:** `go vet`, `gofmt` and the tests, natively on Linux amd64, Linux arm64 and macOS arm64; the `checkout` action run as a consumer's job runs it, for the run's own commit, on Linux and macOS; and a build of every program for Linux amd64 and arm64, macOS arm64 and Windows amd64. The organization's own pull requests run on Blacksmith, `blacksmith-2vcpu-ubuntu-2604`, `blacksmith-4vcpu-ubuntu-2604-arm` and `blacksmith-12vcpu-macos-26`; a fork's on GitHub's `ubuntu-26.04`, `ubuntu-26.04-arm` and `macos-26`.
- **`release.yml`, on pushes to main:** the same, by calling `ci.yml`, then it moves `v1` to the commit. It runs one at a time, and moves `v1` only forward: the new commit must descend from the one `v1` names. It runs only in the organization's own repository, by its owner's ID and name, so a fork's main never tries.

GitHub's rulesets name who may bypass them by account or App, not by workflow, and the ordinary `GITHUB_TOKEN` of any workflow acts as the same GitHub Actions App, including a same-repository pull request's workflow, which may ask for write access. So `v1` is moved by a GitHub App of its own, "Lanescape Actions", installed only on this repository, with Contents read and write and nothing else. Its private key is a secret of the `release` environment, which only the `main` branch may deploy to, so only workflows on `main`, which are reviewed, can use it. `release.yml` is the only one that does. No job that uses the `release` environment ever runs a contribution's code, or any code not on `main`. The release job checks nothing out: it gets the App's token with `actions/create-github-app-token`, from the environment's variable `RELEASE_APP_ID` and secret `RELEASE_APP_PRIVATE_KEY`, for Contents write on this repository alone, and calls GitHub's API with `gh`. It confirms the commit is still on `main`, then creates `v1` if there's none, or, if the commit descends from the one `v1` names, updates it with `force` false, so that GitHub itself refuses anything but a fast-forward. A `v1` that names anything but a commit stops it, for a maintainer to look at. A tag ruleset stops anyone but that App creating, updating or deleting `v*` tags, so moving `v1` takes the same review as merging to main.

That matters because these actions run inside consumers' own jobs, beside whatever those jobs hold: whoever can merge here can change code in every consumer's jobs, which is the risk of a moving tag, and why moving it takes a merge.

Whoever merges to main releases. No agent reviews, approves or merges a pull request without the explicit instruction of the person it works for, for that pull request.
