# Code, tests and releases

## Code

Go, at the latest stable release, pinned by `go.mod`'s `toolchain` line. One module, `github.com/lanescape/actions`, with each action's `action.yml` and program in `<name>/`. It depends on `github.com/lanescape/runners` at a version `go.mod` names, for the interface's constants in its `endpoints` package and for the emulators the tests run against. The service's interface for actions, its spec 0005, is what the actions may rely on; nothing else of the service's. The only other actions they use are `actions/setup-go`, and `actions/github-script`, pinned by full commit SHA, to start the program that speaks the runner's Actions cache (specs/0001-actions.md, Stores).

## Tests

Every behaviour in specs/0001-actions.md has a test. No test runs or calls the real runner service. They run against `lanescape/runners`' own emulators, at the version `go.mod` names, never anyone else's: its emulator of the service's interface for actions, `emulators/service`, which serves binding, the cache's three requests in the `service` store and in index stores, and the `service` store's URLs for resumable uploads and ranged downloads, and its emulators of GitHub and GitHub's OIDC issuer, as that repository's spec 0005 (Testing against the emulator) asks of consumers. Its conformance suite, `conformance/`, runs the same cases against that emulator and against the real service in its own CI, and both must pass every one, so what the actions do against the emulator at a version is what they do against the service at that version, as far as the interface goes. The actions rely on that suite for it, and don't run the service themselves. End-to-end tests run each action as GitHub would, inside the organization and outside it: a pull request's run through to its saves, a fork's run falling back to GitHub's runners, a fork's pull request into an organization repository, an approved contribution, the service answering that GitHub couldn't be reached, and the cache in the `service` store: a pull request restoring main's entry and saving its own, a download or upload cut off and resumed, a URL that expires mid-download, an entry whose SHA-256 doesn't match, an archive whose members reach outside its paths, a failed job whose entry is never restored, a lookup followed by a restore of the same entry, a skipped save, and files whose times differ within a second coming back with their times unchanged. The `actions` store has its own: an entry saved to the Actions cache, recorded, and restored by a later run; a miss, an answer for a key that only starts with the one asked for, an error part-way through a read, and a runner with no Actions cache, each `missing`; bytes whose size or SHA-256 isn't the record's, and more bytes than the record's, each `mismatch`, with nothing left in the paths or `$RUNNER_TEMP`; an upload cut off and resumed; a save that the cache service refuses, which records nothing and doesn't fail the job; a refused save whose content address already holds the same archive, which is recorded after it's read back, and one whose address holds other bytes, which isn't; a `read` run, which packs nothing; a lookup, which fetches nothing; nothing logged at debug level but what the job's other steps log; the default store on and off the service's machines; and `store: service` off them, which fails. These run against the emulator of GitHub's Actions cache service in `lanescape/runners`' GitHub emulator, which follows the requests `actions/cache` v6.1.0 makes and GitHub's scoping of caches, with the service emulator reading that same GitHub (its spec 0005, One GitHub for both). CI also saves entries, small and large, through the program on the runners it uses, and reads them back, against those runners' real Actions cache. The actions' tests run natively on Blacksmith's Linux amd64, Linux arm64 and macOS arm64 machines, since paths, shells, signals and file locking differ between them, and CI builds every program for every platform it targets.

Moving to a newer `lanescape/runners` is an ordinary pull request that changes `go.mod`, so the tests show the actions still work with that version's emulator, which that version's conformance suite holds to its service, before anything relies on it.

## CI and releases

Workflows here run on Blacksmith, never on the runner service's own machines, so a broken service can never stop its actions being fixed. A pull request from a fork runs on GitHub's runners instead; it needs no credentials, since nothing in CI does.

- **`ci.yml`, on pull requests:** `go vet`, `gofmt` and the tests.
- **`release.yml`, on pushes to main:** the same, then it moves `v1` to the commit. It runs one at a time, and moves `v1` only forward: the new commit must descend from the one `v1` names.

GitHub's rulesets name who may bypass them by account or App, not by workflow, and the ordinary `GITHUB_TOKEN` of any workflow acts as the same GitHub Actions App, including a same-repository pull request's workflow, which may ask for write access. So `v1` is moved by a GitHub App of its own, "Lanescape Actions", installed only on this repository, with Contents read and write and nothing else. Its private key is a secret of the `release` environment, which only the `main` branch may deploy to, so only workflows on `main`, which are reviewed, can use it. `release.yml` is the only one that does. No job that uses the `release` environment ever runs a contribution's code, or any code not on `main`. A tag ruleset stops anyone but that App creating, updating or deleting `v*` tags, so moving `v1` takes the same review as merging to main.

That matters because these actions run inside consumers' own jobs, beside whatever those jobs hold: whoever can merge here can change code in every consumer's jobs, which is the risk of a moving tag, and why moving it takes a merge.

Whoever merges to main releases. No agent reviews, approves or merges a pull request without the explicit instruction of the person it works for, for that pull request.
